Skill-ის დასაწერად პროგრამისტი არ უნდა იყო. უმარტივეს შემთხვევაში საკმარისია საქაღალდე და მასში ერთი ტექსტური ფაილი. თუმცა კარგად მომუშავე skill-სა და საერთოდ არ ამოქმედებად skill-ს შორის განსხვავება ხშირად ერთ წინადადებაშია დამალული: აღწერაში. ამ სტატიაში ნულიდან პატარა, მაგრამ რეალურ skill-ს ვწერთ.

## ნაბიჯი 1: შექმენი საქაღალდე და SKILL.md

Agent Skills-ის სპეციფიკაციის მიხედვით, skill არის საქაღალდე, რომელშიც მინიმუმ ერთი SKILL.md ფაილია. ფაილის უკიდურეს დასაწყისში YAML წინასწარი ინფორმაცია (frontmatter) მდებარეობს და ორი ველი სავალდებულოა:

- **name:** მაქსიმუმ 64 სიმბოლო. მხოლოდ პატარა ასოები, ციფრები და ტირე. ტირეთი ვერ დაიწყება და ვერ დასრულდება, ვერ შეიცავს ზედიზედ ორ ტირეს და საქაღალდის სახელს უნდა ემთხვეოდეს. Claude-ის დოკუმენტაცია ასევე აღნიშნავს, რომ სახელში სიტყვები „anthropic“ და „claude“ ვერ გამოიყენება.
- **description:** ცარიელი ვერ იქნება, მაქსიმუმ 1 024 სიმბოლო. უნდა აღწეროს, რას აკეთებს skill და როდის უნდა გამოიყენონ.

არსებობს სურვილისამებრ ველებიც (license, compatibility, metadata და ექსპერიმენტული allowed-tools), მაგრამ უმეტეს skill-ს ისინი არ სჭირდება.

## ნაბიჯი 2: აღწერა გულდასმით დაწერე

რატომ არის აღწერა ასე მნიშვნელოვანი? იმიტომ, რომ აგენტი დასაწყისში თითოეული skill-ის მხოლოდ სახელსა და აღწერას კითხულობს. agentskills.io-ს ფორმულირებით, ამოქმედების „მთელი ტვირთი“ აღწერაზეა. თუ აღწერა არ ამბობს, როდის გამოდგება ეს საქმე, აგენტი ამ skill-ს არ მიუახლოვდება.

წყაროების რჩევები ასე შეიძლება შეჯამდეს:

- დაწერე როგორც **რას აკეთებს**, ისე **როდის გამოიყენება**.
- Claude-ის დოკუმენტაცია გვირჩევს აღწერა **მესამე პირში** დაიწეროს, რადგან ის სისტემურ პრომპტში ემატება („ამუშავებს Excel ფაილებს“, და არა „შემიძლია დაგეხმარო“).
- agentskills.io გვირჩევს, პირდაპირ ჩამოითვალოს ისეთი შემთხვევებიც, როცა მომხმარებელი ამ სფეროს სახელით არ ახსენებს.
- გახადე მოკლე: რამდენიმე წინადადება, მაქსიმუმ მოკლე აბზაცი. Claude Code სიაში აღწერას 1 536 სიმბოლოზე ჭრის, ამიტომ ყველაზე მნიშვნელოვანი გამოყენების შემთხვევა დასაწყისში უნდა იყოს.

## ნაბიჯი 3: ძირითადი ტექსტი მოკლე, სკრიპტი ჭკვიანი

მაგალითად წარმოვიდგინოთ skill, რომელიც ამ ბლოგის საკუთარ წერის წესს მიჰყვება: ტექსტში გრძელი ტირე (em dash) და საშუალო ტირე (en dash) არ უნდა დარჩეს. საქაღალდის სტრუქტურა ასეთი იყოს:

```
tire-denetimi/
├── SKILL.md
└── scripts/
    └── tire_bul.py
```

SKILL.md ფაილი კი მხოლოდ ამდენია:

```markdown
---
name: tire-denetimi
description: ბლოგის სტატიებში პოულობს გრძელი ტირის (U+2014) და საშუალო ტირის (U+2013) გამოყენებას და გასწორებას გვთავაზობს. გამოიყენება, როცა მომხმარებელი Markdown სტატიას გამოსაქვეყნებლად ამზადებს, როცა ამბობს „შეამოწმე ტირეები“, „წერის წესებს შეესაბამება?“, ან როცა სახელს არ ახსენებს, მაგრამ გამოქვეყნებამდე ბოლო შემოწმებას ითხოვს.
---

# ტირეების შემოწმება

1. გაუშვი ბრძანება `python scripts/tire_bul.py <dosya.md>`.
2. გამოსავალში თითოეული ხაზისთვის შესთავაზე ტირის შეცვლა წერტილით, მძიმით, ორწერტილით ან ფრჩხილებით.
3. ნუ შეცვლი აზრს. ხაზები, რომლებშიც დარწმუნებული არ ხარ, მომხმარებელს ჰკითხე.
4. ბოლოს ერთი წინადადებით შეატყობინე, რამდენი ხაზი გაასწორე.
```

Claude-ის დოკუმენტაცია კონტექსტის ფანჯარას „საერთო რესურსად“ განიხილავს და გვირჩევს, დაემატოს მხოლოდ ის ინფორმაცია, რომელიც მოდელმა უკვე არ იცის. ძირითადი ტექსტი 500 ხაზზე ნაკლები უნდა იყოს. გრძელი საცნობარო ტექსტები ცალკე ფაილებში უნდა გადავიდეს და ამ ფაილებზე SKILL.md-იდან ერთდონიანი ბმული უნდა მიეცეს.

სკრიპტებისთვის წესიც მკაფიოა: „გადაწყვიტე, ნუ გადააგდებ“. ანუ სკრიპტმა შეცდომის შემთხვევები თავად უნდა დაამუშაოს და არ უნდა დაიწეროს „დაეშვას, Claude რამეს მოიგონებს“ ლოგიკით. სკრიპტის გაშვებისას კონტექსტში თავად კოდი კი არა, მხოლოდ მისი გამოსავალი შედის. ეს სკრიპტს განმეორებადი და შეცდომის მიმტევებელი საქმეებისთვის ინსტრუქციაზე უფრო სანდოს ხდის.

> **იცოდი?** Claude Code-ში ძველი „მორგებული დახრილი ხაზის ბრძანებები“ skill-ებს შეერწყა. .claude/commands/deploy.md ფაილი და .claude/skills/deploy/SKILL.md ერთსა და იმავე /deploy ბრძანებას ქმნის. თუ არ გინდა, რომ skill ავტომატურად ამოქმედდეს, frontmatter-ში დაამატე disable-model-invocation: true და მხოლოდ ხელით გამოიძახე.

## ნაბიჯი 4: გატესტე, შემდეგ ისევ გატესტე

Claude-ის საუკეთესო პრაქტიკების გზამკვლევი გვირჩევს, გრძელი დოკუმენტის დაწერამდე შეფასების სცენარები მოამზადო, ხოლო გამოქვეყნებამდე შემოწმების სიაში მინიმუმ სამი შეფასება და Haiku-ზე, Sonnet-სა და Opus-ზე ცალ-ცალკე ტესტირებაა. მიზეზი მარტივია: ინსტრუქცია, რომელიც Opus-ზე უნაკლოდ მუშაობს, Haiku-სთვის მეტ დეტალს შეიძლება საჭიროებდეს.

ამოქმედების გასატესტად agentskills.io-ს რჩევა კონკრეტულია: მოამზადე დაახლოებით 20 ნიმუში მომხმარებლის შეტყობინება. მათგან 8-დან 10-მდე skill-ს უნდა ამოქმედებდეს, 8-დან 10-მდე კი არა. ყველაზე ღირებული უარყოფითი მაგალითებია ისინი, რომლებიც „ოდნავ აცდება“, ანუ იგივე სიტყვებს შეიცავს, მაგრამ სხვა საქმეს ითხოვს. რადგან მოდელის ქცევა ყოველ ჯერზე ერთნაირი არ არის, რეკომენდებულია თითოეული შეტყობინების რამდენჯერმე (დასაწყისისთვის 3-ჯერ) გაშვება და ამოქმედების მაჩვენებლის დათვალიერება.

| ცუდი აღწერა | კარგი აღწერა |
|---|---|
| „ეხმარება PDF-ებთან.“ | ამბობს, რას აკეთებს და როდის გამოიყენება |
| მხოლოდ ტექნიკური დეტალები | მომხმარებლის განზრახვას აღწერს |
| ყველაფერს მოიცავს | ისიც მიუთითებს, რას არ აკეთებს |

დაყენებაც მარტივია: Claude Code-ში საკმარისია საქაღალდე მოათავსო ~/.claude/skills/ ქვეშ (პირადი) ან პროექტის .claude/skills/ საქაღალდეში. Claude Code ამ საქაღალდეებს აკვირდება და ცვლილებებს ხელახლა გაშვების გარეშე, იმავე სესიაში აღიქვამს. claude.ai-ზე კი skill-ის zip-ად ატვირთვა პარამეტრებიდან შეგიძლია.
